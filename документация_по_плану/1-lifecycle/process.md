# Process

## Підхід

Для ШІ-помічника підходить інкрементна модель з короткими ітераціями. Dota 2 регулярно оновлюється, тому продукт випускати невеликими завершеними частинами, перевіряти та корегувати за зворотним зв'язком.

## Модель життєвого циклу

Спрощено за ISO/IEC/IEEE 29148:

1. **Ідея та дослідження** — визначати проблему, користувачів, обмеження та гіпотези.
2. **Вимоги та планування** — описати сценарії, критерії прийняття та пріоритети.
3. **Архітектура та прототип** — узгодити модулі, дані, API та інтерфейс.
4. **Інкрементна реалізація** — випускати завершені функції для користувача.
5. **Перевірка** — верифікація вимог, тестування та валідація корисності.
6. **Випуск та супровід** — оновлювати дані, відслідковувати дефекти та враховувати нові патчі.

## Методологія команди

Для реалізації використовується спрощений **Scrum**:

- **Ролі**: Власник продукту, Аналітик, Архітектор, Розробник, Тестувальник, DevOps, Проєктний менеджер.
- **Події**: планування спринту, коротка щоденна встріч, ревʼю інкременту, ретроспектива.
- **Артефакти**: беклог продукту, беклог спринту, інкремент.

Альтернатива — дошка **Kanban** для візуалізації потоку задач.

У невеликій команді один учасник може поєднувати кілька ролей, але відповідальність має бути призначена явно.

## RACI для MVP

| Робота | R | A | C | I |
|---|---|---|---|---|
| Пріоритети MVP | Власник продукту | Власник продукту | Аналітик, архітектор | Вся команда |
| Архітектура | Архітектор | Власник продукту | Розробник, тестувальник | Вся команда |
| Реалізація сценарію | Розробник | Архітектор | Аналітик, тестувальник | Власник продукту |
| План тестування | Тестувальник | Архітектор | Аналітик, розробник | Власник продукту |
| Випуск документації | DevOps/менеджер | Власник продукту | Вся команда | Замовник |

На кожну задачу призначається рівно один `A`. З консультантами (`C`) звʼязуються до початку роботи.

## Правила взаємодії

- вимоги, рішення та домовленості зберігаються в репозиторії;
- робота ведеться через окремі гілки та Pull Request;
- перед злиттям виконується ревʼю;
- зміни регулярно збираються і перевіряються;
- якщо учасник застряг приблизно на дві години, він повідомляє команду;
- на короткій зустрічі обговорюються зроблене, наступний крок та блокади.

## Верифікація та валідація

- **Верифікація:** чи правильно реалізовано вимоги та правила розрахунку.
- **Валідація:** чи допомагає результат гравцеві прийняти рішення та зрозуміти пояснення.

Перевірки планувати одночасно з вимогами, а не відкладати на кінець розробки.

## Перехід до супроводу

Інкремент можна випускати, якщо його головний сценарій проходить тести, документація оновлена, версію ігрових даних вказано, а відомі обмеження показані користувачеві. Після патча необхідно повторно оцінити рекомендації та при потребі випустити оновлення.
