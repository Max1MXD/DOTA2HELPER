# Review Report — Рев'ю вимог та архітектури

## Чек-лист рев'ю

Кожна вимога має бути:

- [x] атомарною;
- [x] однозначною;
- [x] перевіряємою;
- [x] пов'язаною з джерелом та ідентифікатором;
- [x] узгодженою з іншими вимогами;
- [x] вільною від зайвих проєктних рішень;
- [x] наявним пріоритет та критерії прийняття.

Для нефункціональної вимоги треба вказати число, умови та спосіб вимірювання. Формулювання на кшталт «швидко», «зручно» або «сучасно» без критерію перевірки не приймаються.

## Трасування

Вимога зв'язується з потребою користувача, сценарієм, архітектурним рішенням і тестом. Наприклад, вимога про рекомендацію для обраного героя повинна посилатися на сценарій вибору героя та на тест, який перевіряє коректність відповіді.

## Процес рев'ю

1. Автор додає вимогу в загальний документ.
2. Аналітик перевіряє ясність, атомарність та критерій прийняття.
3. Архітектор перевіряє реалізованість та відсутність передчасної прив'язки до технології.
4. Тестувальник перевіряє, чи можна написати тест.
5. Власник продукту підтверджує пріоритет.
6. Рішення фіксується в історії змін.
