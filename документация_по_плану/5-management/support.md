# Support — Супровід

## Види супроводу

| Вид | Опис | Приклад у проєкті |
|---|---|---|
| Коригувальний | Виправлення дефектів | Закриття DEF-001..DEF-00N |
| Адаптивний | Адаптація до змін середовища | Оновлення даних після патчу |
| Еволюційний | Нові функції після MVP | Оверлей, експорт, кеш |

## План підтримки після релізу

Після оновлення гри команда:

1. Фіксує нову версію патча.
2. Перевіряє джерело та повноту даних.
3. Запускає регресивні тести.
4. Пересматриває правила рекомендацій.
5. Оновлює документацію та CHANGELOG.
6. Повідомляє користувачів про непідтверджені або тимчасово відключені функції.

## Канали підтримки

- GitHub Issues — дефекти та запити.
- GitHub Discussions — питання користувачів.
- README — посилання на прототип і документацію.

## Пріоритети інцидентів

| Пріоритет | Опис | Час реакції |
|---|---|---|
| P1 | Критичний: неправильні рекомендації | ≤ 24 год |
| P2 | Високий: некоректна валідація | ≤ 3 днів |
| P3 | Середній: UI/UX зауваження | ≤ 7 днів |
| P4 | Низький: пропозиції | Наступний інкремент |

## Згодування змін із замовником

Зміни, що впливають на Must-вимоги, погоджуються з замовником на рев'ю інкременту. Рішення фіксуються в `1-lifecycle/changes.md`.

## Класифікація звернень

Звернення користувачів класифікуються як:
- дефект даних;
- дефект інтерфейсу;
- дефект вимог;
- запит на нову функцію.

Кожне звернення отримує пріоритет та відповідального.
